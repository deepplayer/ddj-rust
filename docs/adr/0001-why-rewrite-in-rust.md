# ADR-0001：为什么用 Rust 重写而不是改造 Java

- 状态：已接受
- 日期：2026-10-24

## 背景

原服务端是 6 个独立 JVM 进程（`platform` / `game` / `cross` / `hall` / `battle` / `world`），
合计 5034 个类、115 个 Handler 类 / 1705 个 Handler 方法，协议是 Netty + 自定义帧，
跨服用 Hessian（Java 专有二进制），配置散落在 63 个 XML 里。

## 选项

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 保持 Java，只做修复 | 零迁移成本 | 6 进程 × 8 GB 堆 = 48 GB 常驻；XML + 反射难以静态验证 |
| B. Java 重构成单体 | 部署简单 | 仍是 JVM，冷启动 114 s，堆无法按模块裁 |
| C. Rust 重写 | 单二进制、按需裁剪、编译期校验 | 5034 类要重写（真实工作量在业务层） |

## 决定

选 C，但**分层推进**：先建 32 个 crate 的骨架并让全量编译通过，
再按模块灌业务，避免"重写一半不能跑"。

## 后果

- 好的：协议层、配置层、分发层可以完全自动化（proto 生成 / CSV codegen / `inventory` 注册）；
  6 个进程可裁成 7 个 bin 也可合并成 1 个，只由配置决定。
- 坏的：3224 个纯业务类必须手工重写，这是主要成本，没有捷径。
- 缓解：领域层不依赖 tokio/DB，可以先写纯函数单测，再接 IO。
