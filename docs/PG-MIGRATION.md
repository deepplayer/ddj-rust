# MySQL → PostgreSQL 迁移对照

原服务端是 MySQL（`data/sql/platform.sql`，277 表）。本项目统一到 PostgreSQL，
迁移面收敛在**仓储层 + DDL + 连接串**三处，领域层与协议层完全不受影响。

## 1. SQL 语法差异（仓储层唯一要改的地方）

| MySQL | PostgreSQL | 说明 |
|---|---|---|
| `?` 占位符 | `$1` `$2` … | 位置显式化，同一参数可重复引用 |
| `ON DUPLICATE KEY UPDATE num = num + VALUES(num)` | `ON CONFLICT (k) DO UPDATE SET num = t.num + EXCLUDED.num` | 冲突目标必须显式写出来 |
| `LAST_INSERT_ID()` | `RETURNING id` | 插入即返回，省一次往返 |
| `IFNULL(a, b)` | `COALESCE(a, b)` | |
| `GROUP_CONCAT(x)` | `STRING_AGG(x, ',')` | |
| `LIMIT n, m` | `LIMIT m OFFSET n` | 顺序反了，容易写错 |
| 反引号 `` `col` `` | 双引号 `"col"` 或裸标识 | `user` 在 PG 里是保留字，必须 `"user"` |
| `INSERT IGNORE` | `ON CONFLICT DO NOTHING` | |

## 2. DDL 类型映射

277 张平台表由 `tools/mysql2pg.py` 从 `data/sql/platform.sql` 机械转换，映射规则如下：

| MySQL | PostgreSQL | 说明 |
|---|---|---|
| `tinyint(1)` / `tinyint(4)` | `smallint` | **不映射 boolean**：原库拿它当状态位/枚举，转 boolean 会改变语义 |
| `smallint` / `mediumint` | `smallint` / `integer` | |
| `int(n)` | `integer` | 显示宽度 `(n)` 丢弃，PG 无此概念 |
| `int unsigned` | `bigint` | 取值范围变大，避免加 CHECK 影响写入 |
| `bigint(n)` | `bigint` | |
| `bigint unsigned` | `numeric(20)` | 唯一一处（`bf_gift.dbId`）；它是自增列，实际落成 `bigint` |
| `AUTO_INCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` | identity 只接受 smallint/integer/bigint |
| `decimal(p,s)` | `numeric(p,s)` | |
| `float(p,s)` | `real` | PG 的 real 不接受精度参数 |
| `varchar(n)` / `char(n)` | 同左 | |
| `text` / `mediumtext` / `longtext` | `text` | |
| `date` / `datetime` | `date` / `timestamp` | 源库没有 `datetime` 列，时间都用 varchar/bigint 存 |
| `PRIMARY KEY (...) USING BTREE` | `PRIMARY KEY (...)` | `USING BTREE` 删除 |
| `KEY \`n\` (a, b(191))` | `CREATE INDEX "表名_索引名"` | PG 索引名是 schema 级唯一，必须加表名前缀；前缀长度 `(191)` 丢弃 |
| `UNIQUE KEY` | `CREATE UNIQUE INDEX` | |
| `FULLTEXT KEY` | 普通 btree | 只有 1 处（`bf_activity.server_id`），只用于后台模糊搜索，不引入 extension |
| `ENGINE=` / `DEFAULT CHARSET` / `ROW_FORMAT` | 删除 | |
| `COMMENT '...'` | `COMMENT ON TABLE/COLUMN` | 中英混排原文保留 |

## 3. 踩过的坑：`CHECK` 与 `ON CONFLICT` 不能照搬

MySQL 的经典写法：

```sql
INSERT INTO item (player_id, template_id, num) VALUES (?, ?, ?)
ON DUPLICATE KEY UPDATE num = GREATEST(0, num + VALUES(num));
```

原样翻成 PG 后，用 `delta = -100` 扣道具会直接报错：

```text
new row for relation "item" violates check constraint "item_num_check"
Failing row contains (3, 900000001, 11002, -100).
```

原因：`item.num` 上有 `CHECK (num >= 0)`，PostgreSQL 会**先校验待插入元组**，
再走冲突分支。所以负数 delta 在 `VALUES` 里就已经违规了。

正解是「插入值夹一次、更新时用原始参数」：

```sql
INSERT INTO item (player_id, template_id, num) VALUES ($1, $2, GREATEST(0, $3))
ON CONFLICT (player_id, template_id)
DO UPDATE SET num = GREATEST(0, item.num + $3);
```

注意 `DO UPDATE` 里必须用 `$3` 而不是 `EXCLUDED.num`——后者已被夹成 0，
扣减会变成「扣 0」。这条在本仓库 `crates/data/repo/src/pg.rs`
与 `crates/data/db/tests/pg_live.rs` 都有回归测试。

## 4. 迁移（migrations）约定

- 目录：`crates/data/db/migrations/`，文件名 `<版本号>_<描述>.sql`；
- **已进入主干的迁移文件不可修改**，只允许追加新版本（否则 `VersionMismatch`）；
- 迁移同时应用到 `platform` 与 `game_7010544` 两个库，因此 DDL 必须幂等
  （`CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`）；
- 本地开发重置：`psql -c 'drop schema public cascade; create schema public;'`。

## 5. 验证方式

集成测试按 `DATABASE_URL` 是否设置决定跑不跑，CI 没有 PG 时自动跳过：

```bash
export DATABASE_URL='postgres://game:pass@127.0.0.1:5432/platform'
cargo test -p ddj-db --test pg_live

# 覆盖：迁移幂等、ON CONFLICT 累加、GREATEST 夹零
```

## 6. 全量平移（277 张表）

已经完成，不需要手工做。

```bash
# 重新生成（源 DDL 变了才需要跑）
python3 tools/mysql2pg.py \
    --src ../data/sql/platform.sql \
    --schema crates/data/db/migrations/0002_platform.sql \
    --seed   crates/data/db/migrations/0003_platform_seed.sql
```

产物：

| 文件 | 内容 |
|---|---|
| `0002_platform.sql` | 277 张表 + 257 个索引 + 列注释，全部 `IF NOT EXISTS` 幂等 |
| `0003_platform_seed.sql` | 722 行种子数据（`ON CONFLICT DO NOTHING`）+ 自增序列校正 |

### 两个顺序陷阱

1. **序列校正必须放在数据之后**。种子数据带显式 id，`GENERATED BY DEFAULT AS IDENTITY`
   不会自动推进。把 `setval` 放在 `0002` 末尾会让 `0003` 的插入与种子 id 撞车。
2. **`identity` 只接受 smallint/integer/bigint**。`bigint unsigned` 先映射成
   `numeric(20)`，如果是自增列要降回 `bigint`，否则建表直接报
   `identity column type must be smallint, integer, or bigint`。

### 与源库的一致性验证

在远端同时跑了 MySQL 5.7（导入原始 `platform.sql`）和 PostgreSQL 16，逐表比对：

| 项目 | 结果 |
|---|---|
| 表数 | 277 / 277 |
| 列名与顺序（逐表拼接后 diff） | **完全一致**，2409 列 |
| 逐表行数（277 张表逐条 `count(*)`） | **完全一致**，37 张非空表共 722 行 |
| 中文与转义数据 | 抽查 `bf_activity.commonData`，`\"` 正确还原为 JSON |

`pg_live.rs` 里 `platform_schema_is_fully_translated` 把表数（281）、列数（≥2409）、
种子行数（11+100+79）和 identity 序列都锁成了断言，改动源 DDL 后测试会立刻失败。

### 仍然不做的

- 原库的 `bf_server` 表里存着各服的 MySQL 账号密码明文，迁移时原样保留 ——
  这是原系统设计，不在这次迁移范围内改动；
- 存储过程 / 触发器 / 事件：源 dump 里没有，不需要迁；
- 字符集：原库 `utf8mb4`，PG 统一 UTF-8，无需映射。
